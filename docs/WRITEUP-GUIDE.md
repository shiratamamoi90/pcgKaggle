# WRITEUP-GUIDE — 高評価Writeupの流れと書き方

**目的**: Strategy カテゴリ（Kaggle Writeup 審査・締切 2026-09-13）の提出物をどう書くか。
**方針**: 推測を排し、**実際に高評価を得た提出物と、その審査ルーブリック**だけを根拠にする。

参照した実例と一次資料は末尾 §6。

---

## 1. まず配点を見る — 技術の高度さは主戦場ではない

判定付きWriteupコンペで**唯一、重み付きルーブリックが公開されている**のが NFL Big Data Bowl。
毎年開催・賞金10万ドル・NFL32球団のアナリストが審査する、この形式で最も実績のあるコンペ。

| 評価項目 | 配点 | 問われること |
|---|---|---|
| **Football Score**（＝ドメイン価値） | **30%** | 現場が週次で使えるか。データの複雑さを考慮しているか。**アイデアは独自か** |
| **Data Science Score** | **30%** | 正しいか。**主張はデータで裏付けられているか**。統計手法は適切か |
| **Report Score** | **20%** | よく書けているか。追いやすいか。**動機が明確に定義されているか** |
| **Data Visualization Score** | **20%** | 図表はアクセシブルか。正確か。独創的か |

**★ここが最重要**: 純粋な技術力（Data Science）は **30%**。
残り **70% は「ドメインへの意味づけ・文章・図」**。
2024年の優勝チームは *「我々の年はデータサイエンス部分の配点が20%しかなかった」*と書き、
**モデル改良を締切2週間前に打ち切って、残り全部を提示に使った**と明言している。

Kaggle の Notebook/Analytics 系コンペの審査軸も、名前は違うが同じ場所に収束する。

| 次元 | 問われること |
|---|---|
| Quality of Data Visuals | 図は清潔・自明・一貫したスタイルか。図の種類は伝えたい示唆に合っているか |
| Narration & Storytelling | 読者が示唆を理解できるよう説明・文書化されているか。流れは魅力的か |
| Structure & Presentation | 各部が明確に定義されているか。**主要な示唆が中心にあり、コードは邪魔をしないか** |
| Quality of Insights | 示唆は関連性があり有用で**行動につながるか**。**新奇・意外・直観に反するか** |
| Creativity & Originality | 発想と手法は新しいか。**文体上のリスクや独自の声を評価する** |

**2つのルーブリックの共通項＝実質の採点軸**:

1. **問いの意味（ドメイン価値・独自性）**
2. **主張がデータで裏付けられているか**
3. **文章の明晰さ（動機が定義されているか）**
4. **図の質**

## 2. 高評価Writeupに共通する「流れ」

複数の1位提出物に共通していた並び。**技術から始めない。全部が「動機」から始まる。**

```
① 動機（Motivation）
     └ 現実の観察から始める。「なぜこれが重要か」を最初に定義する
     └ 記憶に残る比喩・枠組みを1つ置く
② approach（何をどう測ったか）
     └ 手法そのものより「なぜその測り方が妥当か」
③ 主要な示唆（Key findings）
     └ 図 → 必ず解釈をつける。図を置きっぱなしにしない
     └ 意外・直観に反する発見を前に出す
④ 検証（なぜこれを信じてよいか）
     └ 既知の事実と照合する／アブレーションで寄与を分解する
⑤ 意味と次の一手（So what?）
     └ 現場が明日どう使えるか
⑥ 付録（コード・詳細）
```

**H2O の1位（データストーリーテリング部門）**は
「動機 → アプローチ → 主要要素 → 成功のコツ」で、
冒頭に**現実の観察**（多くの組織はAI導入の初期段階にある）を置き、
**植物の成長段階になぞらえた記憶に残る枠組み**（Seedling→Vegetative→Budding→Flowering→Ripening）を全体の背骨にしていた。

## 3. 書き方の規則（高評価組が実際に守っていたもの）

### 3.1 分量と密度
- **Big Data Bowl の制約: 本文 2,000語以内・図表10点未満。超過は減点対象。**
  賞金10万ドルのコンペが**この短さ**を課している。長さは価値ではない。
- **コードは付録に隠す。** 本文に置くのは「読者の理解を助ける場合」だけ。

### 3.2 読者を2種類想定する
- 審査員には**技術者でない人が混ざる**（BDBではコーチや元選手）。
- Kaggle 公式の Winning Model Documentation も
  **「技術的背景のある人とない人の両方に有益であることを目指せ」**と書いている。
- → **専門用語を削る。** 削れないものは、初出で1文で定義する。

### 3.3 「So what?」に答える
- 優勝チームの言葉: **「なぜ誰かがこの発見を気にすべきなのか」に答えろ。**
- モデルのアーキテクチャを強調するのではなく、**実用的な価値**を前に出す。
  実例: 「既存のNFL公式ラベルの見逃しタックルの90%を捕捉し、
  **さらに3,566件の未知の守備ミスを発見した**」
  → **信頼性（既知と一致する）と重要性（既知になかったものを見つけた）を1文で同時に立てている。**

### 3.4 図の作り方
- **「1つの優れた実例は、誰も読まない名前と数字の大表より無限に価値がある。」**
- **各図は数秒で伝わること。**
- **すべての図に解釈をつける。** 置きっぱなしにしない。
- 配色・スタイルを**全体で一貫**させる。図の種類は伝えたい示唆に合わせる。

### 3.5 検証は「直観的な妥当性」で示す
- 数学的証明より、**具体例と直観的な検証**を優先する。
  実例: 「一流の守備選手が正しく上位に来ることを確認した」。
- **アブレーション**（乱数種とハイパラを固定し、施策を1つずつ入れて指標を記録）は
  Kaggle 公式が明示的に求めている項目。**どの改良が本当に効いたのかを分解して見せる。**

### 3.6 プロセス
- **モデル作業に締切を切り、残りを全部レポートに使う。** BDB優勝チームは**2週間前**に打ち切った。
- **学術論文を書くつもりで書く。**
- **事情を知らない読者にドラフトを読ませる**（知識の呪いを外すため）。
- **話題をぶらさない。** 一貫した1本のストーリーラインを保つ。

## 5. 我々の手札を、この採点軸に当てる

**正直な前提: 対戦成績の軸では勝てない**（846.1・673位/6,892＝上位9.8%）。
§1 の配点構造では成績は評価の一部でしかなく、
**Data Science 30% + Report 20% + 独自性**が主戦場になる。ここは戦える。

| 採点軸 | 我々の位置 | 使える素材 |
|---|---|---|
| **主張がデータで裏付けられているか** | **最強** | 50提出・対照群つきの検定・事前登録した判定基準・アブレーション |
| **新奇/意外/直観に反する示唆** | **最強** | リーサル見逃しが正しい／探索を積むと弱くなる／忠実度は強さの代理でない／自分より弱いものからは蒸留できない |
| **ドメイン価値（独自性）** | 中 | メタの標準化（175チームが60/60一致）、三すくみ、帯別構成 61,994サイドの実測 |
| **デッキ構築の独自性** | **弱い** | 我々はデッキを乗り換えず既存アーキタイプを使った。**乗り換えを2回検定して2回とも大敗した記録**として書くのが誠実 |
| **図の質** | 未着手 | **ここが最大の未投資領域**。§3.4 に沿って作る必要がある |
| 対戦成績 | 弱い | 673位。隠さず書く |

### 我々の「動機」に置ける現実の観察（§2①）

> **オフラインで良く見えたエージェントほど、ラダーで大きく負けた。**

これは §3.3 の「信頼性と重要性を同時に立てる」型に載る:
- **信頼性**: 我々のクローンは実ラダーのアーキタイプ勝率を **0.7pp 差で再現**した
- **重要性**: **その同じクローンがラダーでは −186.1 Elo だった**

### 書いてはいけないこと

- 673位のエージェントを強かったことにする書き方（§3.2 の読者は見抜く）
- 撤回した結論を消すこと。**撤回の記録自体が「主張はデータで裏付けられているか」の証拠になる**
- 手法の羅列。§2 のとおり**技術から始めない**
