## ③ 技術要素（全世代に共通する中身と設計思想）

提出物は4点だけ: `main.py`（盤面→打つ手を返す）/ `model.pth`（NN重み＝賢さの実体）/
`deck.csv`（60枚）/ `cg/`（公式エンジン）。Kaggleは `agent(obs)->選択` を呼ぶだけ。

- **頭脳 = 小型Transformer（AlphaZero系 2ヘッド）**: `MyModel(d_model, heads, ff, enc, dec)`。
  エンコーダが盤面を理解し **value（勝てそう度, tanh -1〜+1）**、候補手を見るデコーダが
  **policy（各手のスコア）** を出す。言語/画像級の巨大モデルではなく超小型で十分。
- **入力 = スパースベクトル + EmbeddingBag(sum)**: カードを (index, value) の疎な組で表し、
  埋め込みを足し合わせる。「手札に何枚」など集合情報を順序非依存で素直に表現。
- **特徴量エンジニアリング（人手の下駄）**: 「この手で何点入るか」「KOできるか」等の自明な情報は
  NNに再発見させず入力へ直接渡す。学習を楽にする実務テク。
- **本番は greedy（`NN_SEARCH=1`）**: `mcts_agent`（PUCT: 勝率 + c·事前確率/(1+訪問回数)）で先読み可能だが、
  **実測で「本番で深く探索させると弱くなった」**（隠れ情報モデルが粗い＝相手デッキ/手札/サイドを雑に仮定するため、
  良い方策を悪いロールアウトが上書きする）。`build_probe.sh` が提出時に `NN_SEARCH` を 1 に書換える。
  → **ラダーチャンピオンはgreedy。オフライン h2h も既定 NN_SEARCH=1 なので同一エージェントを測っている（交絡なし）。**
- **model soup（重み平均）**: `out = a·A + (1-a)·B`。**同一初期値から派生した(=同一basinの)モデル同士**でのみ有効。
  cross-basin（独立BC同士）は**実測0.0%で完全崩壊**。現soupが有効なのは gen8 が champ 起点のRLだから。

## ③c 2026-07-28 追加：アンカーの無効化と、フィールド指標 clean9 への張り替え

### multiply_lucario への勝率は再現しない（間欠故障）

**まず立てた説明は間違っていた。** `multiply_lucario` / `crustle_lucario` / `crustle_v10` が
壁時計1.5秒の探索予算を持つ（`multiply_lucario/main.py:23 SEARCH_TIME_BUDGET = 1.5`、`:416`）のは
事実で、workers 1/4/12 を振ったら 83.0 / 13.0 / 16.0% と出たので「負荷依存」と結論した。
**これは反証された**：`USE_SEARCH=False` にしても workers=1 で 86.0%（探索ONと同じ）、
探索ONのまま workers=4 でも 84.0% が出る。**並列度は原因ではない。**

**同一条件（workers=4, n=100）を反復した結果が真相**：

```
81.0% / 86.0% / 15.0% / 87.0% / 81.0% / 81.0%    ← 二峰。勾配ではない
```

### 機構（証明済み）と修理

1. `multiply_lucario/main.py:39` が **import時に cwd へ `deck.csv` を書き**、`:55-57` で読み返す
   （`opponents/` 12体でこれをやるのはこの1体だけ）。
2. Pool worker が同時 import すると、1つが **truncate中のファイルを読んで `my_deck = []`**。
3. その worker の相手エージェントは不正なので、**担当した全試合で相手のリワードが `None`＝forfeit**。
4. forfeit 試合は一瞬で終わるので、**壊れた worker がタスクキューを食い荒らす**
   → 40戦中31戦・100戦中86戦が影響。「20%の確率で壊れる」ではなく
   **「壊れた実行ではほぼ全試合が壊れる」**。
5. `h2h_vs_rule.py` の `_play` が `b is None` を **`return 0`＝こちらの負け**と集計していた。
   **相手の自滅をこちらの敗北として数える＝符号が逆。** これが 7〜16% の「大敗」の正体。

**証明**（`scratchpad/mp_traceback.py`）: worker ごとの `len(my_deck)` と失敗数を同時出力すると、
6回中1回、**deck len 0 の worker がいた実行だけが 31/40 失敗**、全workerが60の5回は 0/40。
例外ではなく `NONE-REWARD a=0 b=None`（相手だけ失格）。

**修理**: `_load_mod` で `fcntl.flock` により import を直列化し、`_play` は forfeit / draw を
分離して**率から除外し警告を出す**。**修理後10回反復で forfeit 0/10・72〜83%（平均78.2, sd≈3.8）
＝単峰に収束**（修理前は16回中8回が壊滅、Fisher p<0.005）。
**チャンピオンの真値 ≈78% は記録の「79%」とほぼ一致**＝07-26はチャンピオンだけが健全な実行を引き、
12d/yushin/soup の 18〜24% が汚染実行だった。**この相手は指標として復活可能。**

**無効になったもの**: 記録済みの multiply_lucario 値すべて（79 / 20 / 18 / 24 / 92.5 / D1の16 / D2の75）。
モデルごとの「非対称性」は、どの実行がどちらのモードを引いたかを見ていただけ。
すなわち「6日版だけが固有の頑健性を持つ」も「D1は地雷」も
「workers=12の競合状態バグ、workers=4で解消」も誤り。

**★この節自体が再検証ルールの実例**：条件を変えた反復だけでもっともらしい因果を立て、
**同一条件の反復を省いた**ために誤った結論を一度記録した。説明を思いついた時ほど同一条件で反復する。

  「符号を当てた」という主張はどれも偶然と区別できない。** 新しい主張をする前にここへ戻ること。

- **単発は無効**: 同一tarが 810/575/704（sd118）に散る。ペア[床+挑戦者]同時投入で差を読む。
  （sd118 は 07-13〜14 の弱いモデル帯での値。champion帯では sd≈27 に縮む＝**帯によって違う**。）
- **収束は"平坦化"で判定**（固定17hは誤り）: 差は単調減衰し、15hでまだ+19.4→21.6hで0のことがある。
- **提出は原則ペア**（床=実績tar + 挑戦者）。例外(1本可): 変更が1種類だけ or 残り枠1つだけ（詳細CLAUDE.md）。
  **3本以上を一度に投げない**（追跡は最新2提出、3本目で床が外れ差分が読めなくなる）。
